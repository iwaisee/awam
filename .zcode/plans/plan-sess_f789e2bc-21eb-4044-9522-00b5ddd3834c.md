# Normalize departments & territories into real Neon tables

## Goal
Today two large JSON documents hold the structured data: the departments tree (Sector → Agency → Division → Squad) in the `registry` table, and the geography (Provinces → Districts → Zones → Localities + category rules) in the `app_state` key `coverage`. You get **real relational tables in Neon** for both, while every UI (TerritoriesView, DepartmentManager, FieldGatewayView, CategoriesView, the report wizard) keeps working exactly as it does now.

**Key design decision — "normalize the storage, keep the document contract":** both systems already speak a whole-document protocol (the coverage doc and the registry tree). I keep those contracts intact and only change what's behind them. The database becomes normalized tables; the API still serves/assembles the same JSON shapes. This avoids rewriting the 4,200-line TerritoriesView and 4,300-line DepartmentManager and keeps all name-based references (deep links, report ledger joins) working.

## New tables (added to `src/lib/pg.ts` SCHEMA_DDL + `db/schema.sql`, all idempotent)

**Territories**
- `provinces` — surrogate `id BIGINT GENERATED ALWAYS AS IDENTITY` PK, `name_en` UNIQUE (name is today's identity), plus kind/capital/code/slug/area_km2/population/sla_p1_hours/sla_p2_hours/verification/lifecycle/status/admin_model columns; `boundary`, `tiers`, `agencies` (the province agency map) as JSONB.
- `cities` — `id TEXT` PK (existing string ids like `"sialkot"` are load-bearing: ticket prefixes, category `supported_cities`), `province_id` FK → provinces, status/active_reports/subtext/supervisor/contact/office columns, `agencies` JSONB, `lower(name_en)` unique.
- `zones` — identity today is (city, name): surrogate id PK, `city_id` FK, `lower(name_en)` unique per city, jurisdiction/authority/supervisor/contact/office columns.
- `areas` — `id TEXT` PK (existing area ids), `city_id` FK, nullable `zone_id` FK (no town = today's "General" bucket), name_ur/uc_number/jurisdiction/sub_division/status/supervisor/contact/office columns, `lower(name_en)` unique per city.
- `category_rules` — `id TEXT` PK, all scalar columns; `supported_cities` / `allowed_jurisdictions` / `tags` as JSONB.

**Departments**
- `sectors` (id TEXT PK, slug, name, name_urdu, icon, unit, sort) → `agencies` (id TEXT PK, sector_id FK, code, full_name, headquarters, hq_address, descriptor, province, status, control_hotline, dispatch_email, webhook_url, reports_enabled, maintenance, avg_resolution_hours, `jurisdiction_districts` JSONB, sort) → `divisions` (id TEXT PK, agency_id FK, district, division_name(+_urdu), manager_name/designation, official_phone/extension, control_room_hotline, `coverage` JSONB, counters, sort) → `squads` (id TEXT PK, division_id FK, name, lead_technician, phone, members_count, status, role_class, shift, vehicle_plate, `wards` JSONB, active_tickets, sort).

## New `src/lib/territoriesDb.ts`
- `readCoverageDoc()` — assembles `{ cities, categories, provinces }` from the tables via joins (areas/zones nested into each `CityItem`, exactly the legacy shape). Null/undefined optional fields are omitted so `JSON.stringify` round-trips losslessly.
- `writeCoverageDoc(doc)` — one transaction, **upsert-then-delete-orphans** so renames (which change name-based identity) can't cascade-delete data: 1) upsert provinces by `lower(name_en)` → name→id map; 2) upsert cities by id (resolve `province_id` from the doc's `city.province` name); 3) upsert zones by (city_id, lower name); 4) upsert areas by id (resolve `zone_id` from `area.town`, get-or-create implicit zones); 5) upsert categories by id; 6) delete rows whose keys are absent from the doc (areas → zones → cities → provinces → categories).
- `resetCoverage()` (dev-only truncate).

## New `/api/territories` route (GET + PUT)
Same envelope as today's `/api/state/coverage`: `GET → { value: {cities, categories, provinces} | null, seeded }` (seeded = any province/city rows), `PUT → writeCoverageDoc(body.value)`. No shape validation beyond today's.

## `CoverageContext.tsx` — a ~10-line change
Point the two fetch calls (initial GET at line 895, debounced PUT at line 953) from `/api/state/coverage` to `/api/territories`. Everything else stays: localStorage hydration for instant first paint, 500 ms debounce, echo suppression, all 16 mutators, schema-version guards.

## `departmentsDb.ts` — internals swapped, signatures unchanged
- `readRegistry()` — assembles `CoreSector[]` from the 4 tables (ordered by `sort`); `null` when empty → `/api/departments` GET keeps serving the hardcoded seed with `seeded: false` exactly as today.
- `writeRegistry(data)` — same upsert-then-delete-orphans sync (identity here is the client-minted `id`, stable across renames).
- `resetRegistry()` — truncates the 4 tables (dev-only).
- New `updateSquadStatus(id, status)`; `squadPortal.mirrorAvailabilityToRegistry` switches from read-modify-write-the-whole-tree to this single-row update (removes an existing race).

## One-time migration — `scripts/migrate-json-to-tables.mjs`
Reads the legacy rows still in Neon (`app_state` key `coverage` with your real 292-area tree, and the `registry` row) and unpacks them into the new tables. Idempotent (skips when target tables are already populated). The legacy rows stay untouched as a rollback backup.

## What does NOT change
All 7 existing API routes' external behavior, TerritoriesView, DepartmentManager, FieldGatewayView, CategoriesView, the wizard/landing/profile consumers, report ledger semantics (still stores city/area names), Neon CLI workflow, `.env.local`.
